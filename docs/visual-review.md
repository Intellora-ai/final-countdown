# Screenshot review is deliberate. A changed image is never auto-approved.

P12-T4. This is a rule about people, not a script, which is why it is written
down rather than enforced by one.

## The rule

When `e2e/visual.spec.ts` fails, exactly two things may happen:

1. **The change is a bug.** Fix the code. The baseline does not move.
2. **The change is intended.** A human opens the diff, looks at it, and says
   what changed and why in the commit message. Then the baseline moves, in that
   same commit.

There is no third option, and in particular there is no `--update-snapshots` in
CI. A pipeline that regenerates its own expected images cannot fail: it would
turn every visual regression into a silently committed new baseline, which is
worse than having no screenshots at all because it looks like coverage.

## Why a screenshot gate rots faster than any other

Every other gate here fails with a sentence. This one fails with a picture, and
looking at a picture takes effort that a red build does not automatically buy.
The failure mode is well known and always the same:

```
diff looks confusing -> regenerate -> green -> repeat
```

After three rounds of that the baselines describe whatever the code last did,
and the suite is a very expensive way of asserting that the code equals itself.

So the discipline is the whole feature. The tooling only makes the discipline
possible.

## What the numbers mean

`maxDiffPixelRatio: 0.002` — two pixels in a thousand. Anti-aliasing moves by a
pixel or so between otherwise identical renders, and a zero-tolerance baseline
fails on that noise. 0.2% is far below anything a person would call a layout
change and comfortably above the noise floor.

If a diff is *under* the threshold, nothing fails and nothing is reviewed. That
is intended: the gate exists to catch layout regressions, not to police
sub-pixel rendering.

## Baselines are platform-specific, and are generated by CI

Font rasterisation differs between macOS and Linux. Playwright encodes the
platform in the snapshot filename — `gas-reduced-motion-linux.png` — so a
baseline captured on a laptop can never match a CI run.

Therefore:

- **Never commit a `-darwin` baseline.** `.gitignore` refuses them, so a laptop
  capture cannot be added by accident.
- Baselines come from a CI run and are committed from its artefacts.
- In CI, Playwright **fails** on a missing baseline rather than creating one.
  That is deliberate: a first run that silently wrote its own expectations and
  went green is the exact vacuous pass this repository keeps finding elsewhere.

## Regenerating, when it is genuinely intended

```bash
# Locally, to SEE the diff. The output is never committed.
cd frontend && npx playwright test -c playwright.config.ts e2e/visual.spec.ts \
  --project=reduced-motion
```

Then open the report, look at the three images side by side, and decide. If the
change is intended, take the new images from the CI run's artefacts and commit
them with a message that says what moved and why.

"Regenerated baselines" is not such a message.
